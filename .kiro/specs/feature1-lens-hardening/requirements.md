# Requirements Document

## Introduction

This document specifies the requirements for Feature 1 Lens Engine Hardening enhancements. These improvements enhance the existing Hiring Manager Lens system with five specific capabilities: Gemini-powered AI recommendations, job description quality analysis, raw resume text persistence, latest analysis shortcuts, and resume text caching. The enhancements build upon the existing Feature 1 system which already provides resume analysis with visual hierarchy, ATS integrity, semantic matching, and competitive benchmarking capabilities.

## Glossary

- **Feature1_Engine**: The existing resume analysis engine that processes PDFs and generates scores
- **Gemini_Client**: The AI service integration for natural language generation and coaching
- **Analysis_Record**: A stored resume analysis result with scores, metrics, and recommendations
- **JD_Analyzer**: The job description quality assessment component
- **Resume_Cache**: In-memory LRU cache for parsed resume text to avoid re-processing
- **Heuristic_Recommendations**: Terse, rule-based suggestions generated by the analysis engine
- **AI_Recommendations**: Natural language coaching paragraphs generated by Gemini
- **Quality_Score**: A 0-100 numerical assessment of job description completeness and clarity

## Requirements

### Requirement 1: Gemini-Powered AI Recommendations

**User Story:** As a job seeker, I want actionable coaching advice in natural language, so that I can understand how to improve my resume beyond technical recommendations.

#### Acceptance Criteria

1. WHEN the Feature1_Engine completes analysis, THE Gemini_Client SHALL convert heuristic recommendations into natural language coaching paragraphs
2. WHEN Gemini is unavailable, THE Feature1_Engine SHALL continue to function with heuristic recommendations only
3. THE AI_Recommendations SHALL be limited to exactly 5 coaching points maximum
4. WHEN generating AI recommendations, THE Gemini_Client SHALL include the candidate's actual resume content and current scores in the prompt
5. THE Analysis_Record SHALL store both heuristic and AI recommendations separately in the database
6. FOR ALL AI recommendation requests, THE system SHALL use temperature 0.3 and maximum 400 tokens to ensure consistent, focused output

### Requirement 2: Job Description Quality Analysis

**User Story:** As a job seeker, I want to know if my job description is too vague before running resume analysis, so that I can improve it for better semantic matching results.

#### Acceptance Criteria

1. THE JD_Analyzer SHALL provide a POST /api/feature1/analyze-jd endpoint that accepts job description text
2. WHEN analyzing job descriptions, THE JD_Analyzer SHALL return a quality score from 0 to 100
3. THE JD_Analyzer SHALL assign grades of "excellent", "good", "fair", or "poor" based on quality score thresholds
4. WHEN job descriptions contain fewer than 80 words, THE JD_Analyzer SHALL deduct 30 points and flag as unreliable for semantic matching
5. WHEN job descriptions mention fewer than 3 technical skills, THE JD_Analyzer SHALL deduct 20 points and recommend adding specific stack requirements
6. THE JD_Analyzer SHALL detect and count recognizable technical skills using pattern matching
7. WHEN Gemini is available, THE JD_Analyzer SHALL provide 2-sentence AI feedback on the biggest weakness and how to fix it

### Requirement 3: Raw Resume Text Persistence

**User Story:** As a system administrator, I want raw resume text stored in the database, so that Feature 5 can perform consistency checks and enable cross-feature resume reuse.

#### Acceptance Criteria

1. THE Feature1_Engine SHALL extract and store raw resume text during PDF processing
2. THE Analysis_Record SHALL persist raw_resume_text in the database with a maximum length of 8000 characters
3. WHEN raw resume text exceeds 8000 characters, THE system SHALL truncate to the first 8000 characters
4. THE raw resume text SHALL be available for retrieval through existing analysis endpoints
5. THE Feature1_Engine SHALL populate the raw_resume_text field for all new analyses without breaking existing functionality

### Requirement 4: Latest Analysis Shortcut

**User Story:** As a frontend developer, I want to retrieve the most recent analysis directly, so that I don't need to list all versions first to find the latest one.

#### Acceptance Criteria

1. THE system SHALL provide a GET /api/feature1/candidate/{id}/latest endpoint
2. WHEN requesting the latest analysis, THE system SHALL return the analysis with the highest version number for the candidate
3. WHEN no analysis exists for a candidate, THE system SHALL return HTTP 404 with a descriptive error message
4. THE latest analysis endpoint SHALL return the same response format as the existing analysis retrieval endpoint
5. THE endpoint SHALL perform efficiently using database ordering without loading all candidate analyses

### Requirement 5: Resume Text Caching

**User Story:** As a system user, I want faster resume processing on repeated calls, so that semantic and benchmark analysis don't re-parse the same PDF multiple times.

#### Acceptance Criteria

1. THE Resume_Cache SHALL implement LRU (Least Recently Used) caching with a maximum of 10 entries
2. WHEN parsing resume PDFs, THE system SHALL check the cache first using the file path as the key
3. WHEN a resume is found in cache, THE system SHALL return the cached text and layout blocks without re-parsing
4. WHEN the cache is full and a new entry is needed, THE system SHALL evict the least recently used entry
5. THE Resume_Cache SHALL store both extracted text and layout blocks as a tuple for complete PDF processing results
6. THE caching SHALL be transparent to existing Feature1_Engine functionality and not change the API contract

### Requirement 6: Parser Round-Trip Validation

**User Story:** As a quality assurance engineer, I want to ensure PDF parsing consistency, so that cached and fresh parsing results are identical.

#### Acceptance Criteria

1. FOR ALL cached resume parsing results, THE system SHALL produce identical output to fresh parsing of the same PDF
2. WHEN the Resume_Cache returns cached data, THE extracted text SHALL match character-for-character with fresh parsing
3. THE layout blocks returned from cache SHALL contain the same structure and metadata as fresh parsing
4. WHEN cache corruption is detected, THE system SHALL fall back to fresh parsing and update the cache
5. THE caching mechanism SHALL preserve all PDF processing metadata including font information and positioning data

### Requirement 7: Error Handling and Fallback Behavior

**User Story:** As a system administrator, I want robust error handling for AI services, so that the system continues to function when external dependencies are unavailable.

#### Acceptance Criteria

1. WHEN Gemini API calls fail or timeout, THE system SHALL continue processing with empty AI recommendations
2. WHEN JD analysis encounters invalid input, THE system SHALL return appropriate HTTP error codes with descriptive messages
3. WHEN cache operations fail, THE system SHALL fall back to direct PDF parsing without caching
4. THE system SHALL log AI service failures for monitoring without exposing internal errors to users
5. WHEN API rate limits are exceeded, THE system SHALL gracefully degrade AI features while maintaining core functionality
